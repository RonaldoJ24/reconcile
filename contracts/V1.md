# Reconcile v1 contracts

Frozen for Phases 0–2 on 2026-09-14. Breaking changes require a contract version
change and a recorded migration.

## Input files

All CSV files are UTF-8 without a byte-order mark and follow RFC 4180: the first
record is a header, commas are delimiters, CRLF or LF records are accepted, and
double quotes escape delimiters, line endings, and quotes. Unknown, missing, or
duplicate headers are errors. Blank records are ignored. Dates are exactly
`YYYY-MM-DD`. Timestamps are RFC 3339 with a numeric UTC offset. Money is a base-10
string matching `0|[1-9][0-9]{0,12}` with an optional `.[0-9]{1,2}`; it is converted
to integer centavos without binary floating point or rounding. Currency is exactly
`MXN`.

Required bank columns:

`source_account_id,transaction_id,booking_date,payer_name,reference,amount,currency`

Required invoice columns:

`customer_id,customer_name,invoice_id,issued_date,due_date,balance_as_of,outstanding_amount,currency`

Required credit columns:

`customer_id,credit_note_id,balance_as_of,available_amount,currency`

The credit file may also contain `invoice_id`; an empty value means no explicit
link. Every other cell is required and non-empty. Names and references are bounded
to 200 and 500 Unicode characters respectively. Identifiers are 1–100 characters
from letters, digits, `.`, `_`, `-`, `/`, or `:` after surrounding whitespace is
removed.

A message is one UTF-8 TXT file plus an RFC 3339 `message_time`,
`payment_source_account_id`, and `payment_transaction_id` supplied in the request.
Those fields are recorded as supplied context, never inferred from a filename.
Text is limited to 100,000 Unicode characters. Original bytes and immutable source
hashes are retained; CSV evidence uses a one-based record number and byte interval,
and message evidence uses a Unicode code-point interval plus the original bytes.

Local limits are 2 MiB per file, 10 MiB per batch, 2,000 records per CSV, 6,000
entities per batch, and 10 MiB retained source bytes per workspace. Preview limits
are 1 MiB per file, 4 MiB per batch, 500 records per CSV, 1,500 entities per batch,
5 MiB per workspace, and 50 MiB globally. A batch contains exactly one bank and one
invoice CSV, at most one credit CSV, and at most one message.

## Identity, versions, and snapshots

Every record and query is scoped to the workspace resolved from a server-issued
session cookie. Clients never select a workspace ID. Session tokens contain at
least 256 random bits, are stored only as SHA-256 hashes, expire, and use
`HttpOnly`, `SameSite=Strict`, and `Secure` in preview mode. State-changing requests
also require the session's `X-CSRF-Token` and an allowed same-origin `Origin` when
an Origin is present.

Natural keys are workspace-local:

- payment: `(source_account_id, transaction_id)`;
- customer: `customer_id`;
- invoice: `(customer_id, invoice_id)`;
- credit: `(customer_id, credit_note_id)`;
- source: SHA-256 of kind plus original bytes; an exact hash is a duplicate.

Opening invoice and credit rows are authoritative available balances at
`balance_as_of`; they already include all earlier accounting activity. A repeated
natural key with identical normalized content is a duplicate. Different content is
a conflict: it is retained as an immutable rejected source version, the opening
balance is not overwritten, and affected pending proposals become `STALE`.
Payments booked before a referenced opening snapshot are ineligible for matching.

Each payment, invoice, credit, and source has an integer version. Proposal revision
tokens hash the exact source IDs/hashes and balance versions used. Application must
present that token and the proposal revision. The service locks the payment,
invoices, and credits in stable `(table, UUID)` order, recomputes availability, and
rejects stale tokens.

## Allocation rules

All authoritative amounts are signed 64-bit integer centavos, with accepted inputs
between 0 and 999,999,999,999. Applications must be strictly positive. Cash and
credit are distinct line types. For each active application:

- cash lines plus unapplied cash equal the payment amount;
- total cash used by all active applications cannot exceed the payment;
- cash plus credit applied to an invoice cannot exceed its opening balance;
- credit use cannot exceed the credit note's opening balance;
- all payment, invoice, credit, customer, and workspace relationships agree;
- a credit line targets its explicit invoice link; unlinked credit remains review;
- one proposal has one to three invoices and at most one credit note.

Deterministic matching uses only current records and cited bank/message evidence.
Explicit valid invoice references outrank payer-name and amount signals. An exact
amount alone never identifies an invoice. A single explicitly referenced invoice
may receive a partial cash application. A group is proposed only when all invoices
are explicitly referenced and the cash plus an explicitly linked credit produces a
feasible allocation. Ambiguous, stale, truncated, or unsupported cases are
`NEEDS_REVIEW`; no oldest-first fallback exists.

A correction validates the same financial rules and creates revision `n+1` with a
human provenance record; it never mutates revision `n`. Applied revisions are
immutable. Application and reversal each require a reviewer name and idempotency
key. Reusing a key with the identical canonical payload returns the original result;
reusing it with any other payload returns conflict. Reversal marks the application
group reversed and restores only its active cash/credit lines; history is never
deleted.

## HTTP API

All JSON models reject unknown fields. Errors use
`{"error":{"code":string,"message":string,"fields"?:[...]}}`.

| Method and path | Contract |
| --- | --- |
| `POST /api/v1/session` | Create/restore a workspace session; return mode, expiry, CSRF token. |
| `GET /api/v1/health` | Process liveness only; never queries PostgreSQL. |
| `GET /api/v1/ready` | Auth-independent bounded PostgreSQL/schema readiness. |
| `POST /api/v1/imports/validate` | Multipart files/context; retain immutable sources and return batch ID, row issues, accepted/rejected counts. No business rows are committed. |
| `POST /api/v1/imports/{batch_id}/commit` | Commit only validated accepted rows, record conflicts, enqueue one matching job per accepted payment, return counts and job IDs. |
| `GET /api/v1/imports` | Workspace batch summaries. |
| `GET /api/v1/sources/{source_id}` | Source metadata and bounded text/row evidence; never another workspace's bytes. |
| `POST /api/v1/jobs/run-once` | Claim one due job with `FOR UPDATE SKIP LOCKED` and a lease, process, then return state. Local/private and authenticated only. |
| `GET /api/v1/proposals` | Review queue summaries. |
| `GET /api/v1/proposals/{proposal_id}` | Revision, payment, cash/credit lines, balances, evidence, alternatives, trace, and version token. |
| `POST /api/v1/proposals/{proposal_id}/correct` | Expected revision plus replacement cash/credit lines and reviewer; return a new validated revision. |
| `POST /api/v1/proposals/{proposal_id}/apply` | Expected revision/version token, reviewer, idempotency key; return persisted application. |
| `POST /api/v1/applications/{application_id}/reverse` | Reviewer, reason, idempotency key; return persisted reversal. |
| `GET /api/v1/exports/applications.csv` | RFC 4180 active/history export; spreadsheet-leading `=`, `+`, `-`, or `@` in text is prefixed with `'`. |
| `GET /api/v1/sample` | Download the human-authored synthetic example packet. |

Mutations require CSRF. Missing/expired ownership is reported as 404 for object
lookups. Optimistic, duplicate, and idempotency conflicts are 409; validation is
422; quotas are 413; authentication is 401/403.

## Jobs and model boundary

Jobs have `PENDING`, `RUNNING`, `SUCCEEDED`, or `FAILED`, a lease owner/expiry,
attempt count, maximum attempts, and available-at time. Claim is atomic. Expired
leases can be reclaimed; financial effects remain separately idempotent. The local
worker runs one or a bounded number of jobs and exits unless explicitly asked to
loop. The web process wakes a bounded consumer on enqueue or authenticated activity
without idle database polling.

Phases 0–2 implement `rules-v1` only. No provider SDK, training labels, learned
artifact, confidence claim, or hidden expected allocation may be imported by runtime
code. Rules emit documented signals, alternatives, and `NEEDS_REVIEW`; they never
apply money. ML training begins only in Phase 3 and LLM interpretation only in
Phase 4. Application and reversal always remain deterministic PostgreSQL services.
